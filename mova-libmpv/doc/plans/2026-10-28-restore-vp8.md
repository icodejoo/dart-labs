## 1. 背景与决策

VP8 当年因"遗留格式、无 mediacodec 封装"被砍（`flavors-mova-slim-n9.sh:34`、README L175/L677）。这两条依据现在看都站不住：

- **"无 mediacodec 封装"是错的**（实测）：n9.0.2 `configure:3711` 有 `vp8_mediacodec_decoder_deps="mediacodec"`，`mediacodecdec.c:651` 有 `DECLARE_MEDIACODEC_VDEC(vp8, …)`，`allcodecs.c:910` 注册。
- WebRTC 的强制编码就是 VP8，浏览器推流到 WHEP 服务端时只推 VP8 很常见；存量 WebM 也有（`example/tool/online_sources.json` 里 `webm-vp8-tv1080`、Wikimedia `Big_Buck_Bunny_4K.webm` 现在都是"静默只出声/拒绝"）。

用户已拍板三处都做：

| # | 位置 | 做法 | 依据 |
|---|---|---|---|
| 1 | Android（n9 flavor） | 加 `vp8_mediacodec` + `vp8` parser；**不加** ffmpeg VP8 软解（推荐，见 §1.1） | `vp8_mediacodec` 只依赖 `mediacodec`，不 select 任何东西（`configure:3711`），无需新 bsf |
| 2 | Windows、Linux | `--enable-decoder` 加 `vp8`、`--enable-parser` 加 `vp8`，只做软解 | n9.0.2 里 VP8 只有 `nvdec`/`vaapi` 两个 hwaccel（`configure:3527-3530`），没有 `d3d11va`/`dxva2`，已用 grep 核实 |
| 3 | WHEP | 新增补丁 **0015**（不改 0003）：offer 加 VP8，answer 选 codec 加 VP8，`whep.c` 自写 VP8 RTP 解包 | **WHEP 不用 ffmpeg 的 `rtpdec`，`rtpdec_vp8.c` 用不上**，见 §3 |

### 1.1 Android 要不要 ffmpeg VP8 软解兜底——推荐**不要**

- **理由 1：MediaCodec 这条路本身就带软解兜底**。STG-AL00（Android 12）实查 `/vendor/etc/media_codecs*.xml`：VP8 解码器只有 `c2.android.vp8.decoder`（AOSP 自带，`/system/lib64/libvpx.so`），**没有厂商硬件 VP8 解码器**（实测，仅此一台）。所以"VP8 走 MediaCodec"在这台机上实际是平台 libvpx 软解，质量与 ffmpeg 原生 vp8 软解同级；再塞一份 ffmpeg 软解是重复。Android CDD 要求支持 VP8 解码（按用户说明，我没另行查证），即任何带 MediaCodec 的设备至少有这个平台软解。
- **理由 2：先例一致**。h264/vp9 已是 hw-only，VP9 软解被砍时同样接受"不支持就播放失败"的取舍。
- **理由 3：成本**。ffmpeg vp8 软解 Android 每个 ABI 约 +80～150KB（**推断**：Windows 纯 C `-Os` 实测 +80KB，带 NEON/x86 汇编更大），四个 ABI 都要付。
- **代价/风险**：mediacodec 对奇怪流（分辨率中途变化、并发会话、`hwdec=no`）失败时没有软解可退（与现有 VP9 同）。若真机回归里 VP8 mediacodec 不稳，再追加软解（改动只是 `DECODERS_VIDEO` 加 `vp8`，约 1 行）。
- 回归脚本要保留断言 **`libavcodec/vp8.c` 仍不在 Android 产物里**（证明软解没被意外拉进来）。

## 3. WHEP 的 VP8：现状与方案

### 3.1 去封装现状（关键发现，实测）

1. **WHEP 路径不用 ffmpeg 的 RTP 解包**。`whep.c` 自写解包（README「为什么不用 rtpdec」：链 `rtpdec.o` 会把 asf/rm/qt/mpegts 的 handler 全拖进来，stripped +344KB）。所以 `rtpdec_vp8.c`、`--enable-` 任何 rtp 相关组件都**不需要、也不该启用**。只有 `whep_rx_deliver`（`whep.c:1840`）按 `is_video` 一律调 `whep_h264_input`。
2. **H.264 写死的点（要改的全部）**：
   - offer：`whep.c:~462` `m=video … 102 103 104 112 113 114`；`:469-479` 三档 H264 + RTX；PT 是 102–104 / RTX 112–114，音频 opus 111（`:60`）。0003 patch 里对应 L281/L294。
   - 选 codec：`whep_select_codec`（`:621`）`want = "opus" : "H264"`，按 answer 的 m= 行顺序取第一个匹配的。
   - 建流：`whep_create_streams`（`:927`）`codec_id = AV_CODEC_ID_H264`，并解析 fmtp 的 `profile-level-id`。
   - 解包/起播：`whep_h264_input`/`whep_h264_au_end`（`:1731`/`:1678`）；起播闸门 `seen_key` 要求"带 SPS/PPS 的 IDR"，并按 SPS 回填宽高（0013）。
   - 报错文案：`:721` "no usable opus/H264 media"。
3. **与 H.264 共用、无需改的逻辑**：
   - **PLI**：`pli_on = rtcp_pli && codec.pli && is_video`（`:1352`），起播未见关键帧每秒重试（`:2117`），不可恢复丢包再发（`whep_loss_note` `:1893`）——按 `is_video` 而不是按 codec，VP8 直接复用。
   - **NACK/RTX**：`nack_on = rtcp_nack && codec.nack && rtx_pt < 0`（`:1351`），`rtx_pt` 由 answer 的 `apt=` 找（`:636`）——与 codec 无关。**RTX 仍未实现**：若服务端给 VP8 协商了 RTX，同 H.264 一样不发 NACK、只靠 PLI（MediaMTX 的 answer 无 RTX，浏览器系 SFU 通常有，**会退化**）。
   - 重排、SRTP、RR、consent/存活、丢包后 `au_bad` 标记（`:2190/:2227`）、`first_frame_timeout` 等待（`whep_wait_first_key` `:2501`，只看 `seen_key`）都是 codec 无关。
   - `rx->au` 缓冲与 `whep_h264_add`（只是带上限的追加，`start_code=0` 即纯追加）可直接给 VP8 用。
4. **ffmpeg 侧无需改动**：解包出的是整帧 VP8 裸帧 AVPacket，Windows/Linux 走 `vp8` 解码器，Android 走 `vp8_mediacodec`（`avformat_find_stream_info` 找到的解码器与 H.264 同理，h264 现在就是 hw-only 且工作）。

### 3.2 补丁 0015 方案（只改 `whep.c`）

**为什么新增 0015 而不是改 0003**：0004–0014 的 hunk 上下文都依赖 0003 的 `whep.c`，改 0003 要把后面十一个补丁全部重新 rebase；新增 0015 一个文件、`0*.patch` 通配自动生效，历史可审计。README 补一行。

**编译期守卫**（`#include "config_components.h"` 提供 `CONFIG_*_DECODER`）：

```c
/* 编了 VP8 解码器（软解或 MediaCodec）才在 offer 里提议、才允许选中 VP8 */
#define WHEP_HAVE_VP8 (CONFIG_VP8_DECODER || CONFIG_VP8_MEDIACODEC_DECODER)
#define WHEP_OFFER_PT_VP8      105
#define WHEP_OFFER_PT_VP8_RTX  115
```

**1) offer**（`whep_generate_offer`）：H.264 仍排第一，VP8 在其后，RTX 在最后；不广告 `ccm fir`（FIR 未实现）。

```c
av_bprintf(&bp, "m=video 9 UDP/TLS/RTP/SAVPF 102 103 104%s 112 113 114%s\r\n",
           WHEP_HAVE_VP8 ? " 105" : "", WHEP_HAVE_VP8 ? " 115" : "");
/* …原 H264 三档循环不变… */
if (WHEP_HAVE_VP8)
    av_bprintf(&bp,
        "a=rtpmap:%d VP8/90000\r\n"
        "a=rtcp-fb:%d nack\r\n"
        "a=rtcp-fb:%d nack pli\r\n"
        "a=rtpmap:%d rtx/90000\r\n"
        "a=fmtp:%d apt=%d\r\n",
        WHEP_OFFER_PT_VP8, WHEP_OFFER_PT_VP8, WHEP_OFFER_PT_VP8,
        WHEP_OFFER_PT_VP8_RTX, WHEP_OFFER_PT_VP8_RTX, WHEP_OFFER_PT_VP8);
```

`WHEP_MAX_CODEC`（`:54`，现 8）：offer 恰好 8 个 PT，answer 通常不会超；建议顺手改 12 留余量（零成本）。`WHEP_MAX_SDP_SIZE` 16KB 足够。

**2) 选 codec**：偏好固定 **H264 > VP8**，不跟 answer 的 m= 顺序（防止服务端把 VP8 排前面时 H.264 反被放弃）：

```c
static void whep_select_codec(WhepMedia *m)
{
    static const char *const audio_want[] = { "opus", NULL };
    const char *const video_want[] = { "H264", WHEP_HAVE_VP8 ? "VP8" : NULL, NULL };
    const char *const *want = m->type == AVMEDIA_TYPE_AUDIO ? audio_want : video_want;

    m->sel = -1;  m->rtx_pt = -1;
    for (; *want && m->sel < 0; want++)               /* 按偏好顺序 */
        for (int k = 0; k < m->nb_pts && m->sel < 0; k++)   /* 再按 answer 的 PT 顺序 */
            for (int i = 0; i < m->nb_codec; i++)
                if (m->codec[i].pt == m->pts[k] && !av_strcasecmp(m->codec[i].name, *want)) {
                    m->sel = i;
                    break;
                }
    /* 其余（RTX 查找、nack/pli 合并）保持原样 */
}
```

**3) 建流与 rx**：`WhepRx` 加 `int vp8;`；`whep_rx_setup`（`:1346` 附近）`rx->vp8 = !av_strcasecmp(m->codec[m->sel].name, "VP8")`；`whep_create_streams` 里 `codec_id = c 是 VP8 ? AV_CODEC_ID_VP8 : AV_CODEC_ID_H264`，`profile-level-id` 解析只对 H264 做；VP8 不需要 extradata、不设 `need_parsing`（与 H264 同样的 pts 原因）。

**4) 解包**（RFC 7741；全部是新增的 static 函数，不碰 H.264 路径）：

```c
/* 解析 VP8 payload descriptor（RFC 7741 §4.2）。返回描述符长度，非法返回 -1；start=1 表示帧起点（S=1 且 PID=0） */
static int whep_vp8_desc(const uint8_t *p, int len, int *start)
{
    int n = 1;
    if (len < 1) return -1;
    if (p[0] & 0x80) {                       /* X：有扩展字节 */
        int ext;
        if (len < 2) return -1;
        ext = p[1]; n = 2;
        if (ext & 0x80) {                    /* I：PictureID，M 位决定 1 或 2 字节 */
            if (n >= len) return -1;
            n += (p[n] & 0x80) ? 2 : 1;
        }
        if (ext & 0x40) n++;                 /* L：TL0PICIDX */
        if (ext & 0x30) n++;                 /* T 或 K：TID/Y/KEYIDX */
        if (n > len) return -1;
    }
    *start = (p[0] & 0x10) && !(p[0] & 0x07);
    return n;
}

/* 结束当前 VP8 帧：不完整丢弃；起播前必须是带 9d 01 2a 起始码的关键帧，据此回填宽高；起播后全部输出 */
static void whep_vp8_au_end(AVFormatContext *s, WhepRx *rx);   /* 见下 */

/* 追加一个 RTP 包的 VP8 载荷；时间戳变化或 marker 结束一帧 */
static void whep_vp8_input(AVFormatContext *s, WhepRx *rx, const uint8_t *p, int len,
                           uint32_t ts, int64_t pts, int marker);
```

`whep_vp8_input` 逻辑：同 `whep_h264_input` 的"时间戳变化先结束上一帧、新帧初始化 `au_*`"；`desc<0 || desc>=len` → `au_bad=1`；`start` 包：若 `au_size>0` 说明同帧出现第二个起点 → `au_bad=1`，否则记 `au_key = !(p[desc] & 1)`（VP8 帧标签 bit0 为 0 即关键帧）并追加；非起始包：`au_size==0`（起始包丢了）→ `au_bad=1`，否则追加；`marker` 则 `whep_vp8_au_end`。追加复用 `whep_h264_add(rx, p+desc, len-desc, 0)`。

`whep_vp8_au_end`：`au_bad || au_size<3` → `n_drop_au++`；未起播（`!seen_key`）时必须 `au_key && au_size>=10 && AV_RB24(au+3)==0x9d012a`，否则 `n_nokey++` 丢弃；通过则 `width = AV_RL16(au+6)&0x3fff`、`height = AV_RL16(au+8)&0x3fff` 写进 `codecpar`（为 0 视为非法）、日志沿用 "First video key frame out at …"、`seen_key=1`、`whep_rx_emit(…, key=1)`；起播后 `whep_rx_emit(…, au_key)`。**VP8 不需要 SPS/PPS 缓存**，比 H.264 简单。

**5) 分发**（`whep_rx_deliver`，`:1840`）：`if (WHEP_HAVE_VP8 && rx->vp8) whep_vp8_input(…); else whep_h264_input(…);`；`:721` 报错文案改 "opus/H264/VP8"。

预估代码增量 `whep.o` text **+1.5～2.5KB**（**推断**，参照 0010 的整套 RTCP 反馈才 +3.7KB）。

**已知局限（写进 README）**：VP8 起播要等关键帧（同 H.264，PLI 能否缩短取决于服务端）；关键帧中途改分辨率（simulcast/自适应）不更新 `codecpar`，未验证；丢帧后到下一个关键帧前有花屏，同 H.264；RTX 同上。

**codeup 双远程的 LFS 坑（引用 mova/CLAUDE.md「运维踩坑记录」）**：`origin` 有 codeup + GitHub 两个 push URL，CI 只推 GitHub，**每次 CI 重建后 codeup 必缺新 LFS 对象**，`git lfs push origin` 只会传到其中一个。流程：从 GitHub 取到最新提交与 LFS 内容 → 加一个只指向 codeup 的临时 remote（URL 用 `git remote get-url --all origin` 的第一条）→ `git lfs push <临时remote> main --all` 或按 `--object-id` 推 → 用 `git clone --branch main --single-branch <codeup url> <空目录>` 全新克隆，逐个比对 `libmpv.so`/`libmpv-2.dll` 字节数（唯一可靠验证，`git lfs pull` 有本地缓存会掩盖缺失）。

## 7. 风险与未验证项

1. **WHEP VP8 全链路零验证**：MediaMTX 能否把 VP8 转成 WebRTC、浏览器 VP8 描述符（PictureID/TL0PICIDX/TID）是否被正确剥离、关键帧到达后宽高回填是否被 mediacodec 接受，都要 P1/P3 实测。
2. **RTX**：浏览器系 SFU 对 VP8 通常协商 RTX，我们不发 NACK，丢包只能靠 PLI，会比 MediaMTX 下明显更差（**推断**）。RTX 还原是单独的老欠账（H.264 同样受影响），不在本次范围，建议另立项。
3. **Android 的 VP8 在有的设备上是平台软解**（STG-AL00 实测）：`mediacodec-copy` 下 CPU 占用、1080p 以上流畅度没测；低端机 + 高分辨率可能卡。
4. **`hwdec=no` / mediacodec 打不开时 Android 没有退路**（同 VP9）。
5. **关键帧改分辨率**：WHEP 路径不更新 `codecpar`（H.264 亦然），simulcast 切层可能画面异常，未验证。
6. **Windows 汇编体积**：预算里的 +120～150KB 是推断，真值以 CI 为准。
7. **iOS/macOS 本轮不改**：行为不变（编译期守卫），但 Apple 平台仍播不了 VP8（WHEP 与 WebM 都是）。iOS 真机永远是缺口，没有 Mac 的限制不变。
8. **回归脚本是字符串代理**（`vp8_mediacodec` 名字、`vp8.c` 路径串），不是符号级证据（baseline.md §3.1 已说明）；以真机播放结果为准。
9. **旧文档互相矛盾**：README/`2026-10-02-extreme-slim-config.md:173`（"VP8 不要加"）、`2026-10-01-whep-receiver.md` 的"不做 VP8"都要标注被取代，避免下次又按旧结论改回去。
10. 本机无 MSYS2，Windows 构建只能走 CI；WSL 当前 Stopped，P0 第 2 步需要先启动它。
