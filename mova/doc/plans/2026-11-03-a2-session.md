## 1. 架构决策

### D1 — A22 的搬迁口径：`MovaSession` 先长成 `MovaAds` 的样子，A23 才改签名

- A22 里 `MovaSession(MovaApi api, {MovaCutover? cutover})` 与 `MovaAds` 构造**逐字同签名**，类体整体搬迁；`MovaAds` 留一个 `final MovaSession _session` 字段与转发成员。
- 转发**一律同步返回内部 Future**：`Future<void> load(MovaSource c) => _session.load(c);`，不写 `async { await … }`。理由：原 `MovaAds.load` 本身是 `async` 函数，调用时同步跑到第一个 `await` 再返回 Future；直接返回 `_session.load(c)` 的 Future，内部 async 体照样同步跑到第一个 `await`，完成时机逐微任务相同。包一层 `async` 会多出至少一个微任务（总计划 R-2）。
- 流 getter 返回同一个 broadcast 流实例（`Stream<void> get changes => _session.changes;`），订阅时机不变。
- `MovaAds` 的公开 dartdoc（含示例）**原地保留**；会话成员只写一行中文注释"同 `MovaAds.xxx`"。这样文档行不算搬迁、也不重复，非搬迁行预算可控（见 A22 判据）。

否决：A22 就引入新签名——机械提交里混入行为（自动识别 cutover），违反 3.1 第 3 条。

### D2 — cutover 识别：经 `MovaAds` 构造按显式参数，直接构造自动识别（A23）

- 包内工厂 `MovaSession movaSessionForAds(MovaApi api, MovaCutover? cutover)`：照旧只认显式 `cutover:`。
- 公开构造 `MovaSession(api, …)`：`_cutover = api is MovaCutover ? api as MovaCutover : null`。仍受 `cutoverEnabled` 门控（`MovaCutoverConfig.enabled` 默认关），所以"新功能默认关"不变——直接构造的会话拿到一个关闭的直通代理时，行为等于没有 cutover。
- `session.dart` 在 barrel 里 `export … show MovaSession, MovaLoadOutcome`，`movaSessionForAds` 不出包。

### D3 — `MovaAds.session` 访问口（A23 公开）

- `MovaSession get session` 只读、公开（总计划 2.3 末尾）。A25 的 `MovaPlaylist(api, ads:)` 用它拿共享会话，`MovaPlaylist` 不反向依赖 `MovaAds` 内部。
- 文档写明：经 `ads.session` 调 `load/jumpTo` 与经 `ads.load` 等价；`ads.session.dispose()` 等于 `ads.dispose()`（同一个实例，借用规则不变）。

### D4 — 广告时钟（A18）：Timer 到期 + 注入 `now` 算剩余，只认 `playing` 边沿

- `MovaAdClock` 用 `Timer` 驱动到期（fakeAsync 能推进），用注入的 `now` 算剩余（`DateTime.now` 不跟 fakeAsync）。会话持有 `@visibleForTesting DateTime Function() debugClock = DateTime.now;`，两只时钟以闭包 `() => debugClock()` 取时，测试在构造后改它也能生效（与 `engine.debugClock` 同模式，`engine.dart:408`）。
- 会话订阅 `api.states`，记 `_lastPlaying`（初值取 `api.state.playing`）。只在 `phase == ad`（广告位时钟）或 `phase == pending`（倒计时时钟）时，把 `true→false` 转成 `pause()`、`false→true` 转成 `resume()`。
- **补充（总计划没写）**：时钟起表时若 `api.state.playbackIntent == false`，以暂停态起表，等 `playing` 的 `false→true` 边沿再走。否则"用户暂停时插播的广告（`playAdNow`）"或 A20 以暂停态提交的广告，会在暂停中照样计完时长。替身意图由 A19 维护，现有用例里起表时意图都为真，不受影响。
- `_loadTimer` 保持独立墙钟期限（2.4 表），暂停不停它：广告卡在加载阶段时用户点暂停，不应把"始终没有首帧"的判定无限推后。
- 计费口径变化（暂停期间不计时）写进 CHANGELOG（R-8）。

### D5 — 意图快照（A20）：只看 `playbackIntent`，在 `old.pause()` 之前取

- `_commitNow`：认领后、第一个 `await` 之前 `final wantPlay = old.state.playbackIntent;`。换指后 `wantPlay ? shadow.play() : shadow.pause()`；解静音失败的回退分支 `if (current() && wantPlay) await old.play();`；`_keepAliveWanted && wantPlay` 才给影子 `setKeepAlive(true)`（意图为假时引擎语义是 `pause()` 结束待机，不能先进待机再立刻被 pause 掉）。
- 会话侧：`_resumeAfterAd` 入口取 `_api.state.playbackIntent` 作为续播意图，传给 `_playContent(autoPlay:)` 与 pod 串播的 `_playAd(autoPlay:)`；`load` 起播（前贴片或正片）显式传 `true`；中插、`playAdNow`、后贴片、失败重试在 `_playAd` 入口取快照。
- 不用 `intent || playing`：用户刚按暂停时内核 `playing` 还会真一小会儿，或运算会把暂停吞掉。代价：`engineFactory` 返回不维护 `playbackIntent` 的自写 `MovaApi`（意图恒假）时，换指后影子停在暂停——写进 CHANGELOG 与 `MovaCutoverEngine` 类注释（`MovaState.playbackIntent` 早已是状态契约的一部分）。
- `cutoverTo` 公开动词的回落 `_active.open(source)` 不改（A27 起会话不再调它）。

### D6 — 后台暂停（A21）：MovaPlayer 自带一个最小监听，祖先守卫（同一 api）在场时让位

- `_RenderSurface` 的 `Video` 传 `pauseUponEnteringBackgroundMode: false, resumeUponEnteringForegroundMode: false`（参数名与默认值已在 media_kit_video **2.0.1** 源码核实，见第 0 节第 7 行）。
- `_MovaPlayerState` 持有一个 `AppLifecycleListener`，**只在 `paused`/`detached` 时动作**（与 media_kit 2.0.1 一致，`hidden`/`inactive` 不动），动作前逐条检查：有 `Video` 渲染面（`widget.surface == null && api.renderHandle != null`）、没有同一 api 的祖先守卫、`!state.pip`、`state.playbackIntent || state.playing`，全部满足才 `unawaited(api.pause())`。不自动恢复（与 `resumeUponEnteringForegroundMode` 默认 false 一致）。
- "有渲染面"在**事件发生时**判断，不在挂载时决定是否注册：cutover 换指、lazy `VideoController` 都会让 `renderHandle` 在挂载后才出现。总计划写的"audioOnly 不注册监听"落成"audioOnly 不动作"，测试按行为断言。
- 守卫标记：新文件 `ui/guard/guard_scope.dart`（不导出）放 `MovaGuardScope extends InheritedWidget { final MovaApi api; }` 与 `bool movaGuardedBy(BuildContext, MovaApi)`；`MovaAutoPause.build` 改为 `MovaGuardScope(api: widget.api, child: widget.child)`。只对**同一 api** 让位：feed、小窗这类一个树里多个引擎的场景，外层守卫管不到的引擎仍由各自 MovaPlayer 兜底。
- 同一 api 挂两个 MovaPlayer（页面 + 小窗）：第一个 `pause()` 同步把意图写成假，第二个检查不过，不会重复下发。
- 不给 MovaPlayer 加开关参数：要后台继续出声的宿主用 `MovaAutoPause(config: MovaAutoPauseConfig(background: false))` 包一层，让位规则自然生效（第 10 节第 6 条）。

### D7 — 只提交自己预热的槽：包内能力 `MovaWarmOwner`（A27）

问题：A27 把一次性 `cutoverTo` 换成 `prepare + commit`。F6 保证的是 `cutoverTo` 只提交自己的槽；公开 `commit()` 提交的是**调用时刻的当前槽**（F1 之后是 `_commitSlot(_slot, _op)`）。会话是 prepare/commit 的主要调用方，一旦在 prepare 与 commit 之间槽被换（进度驱动的正片预热、宿主自己的 prepare），会把别的源当成这条广告转正；宿主直接 `open` 让操作代际过期后，公开 `commit()` 只能回 `false`，会话分不清"没就绪"还是"被取代"，会按 `notReadyAction`/硬切把宿主刚打开的源顶掉。

决定：新文件 `core/cutover/owned.dart`（不导出），`MovaCutoverEngine` 实现：

```dart
/// 预热凭据：只认它对应的那一次预热（包内，不导出）。
final class MovaWarmTicket {
  MovaWarmTicket._(this._slot, this._op);
  final Object _slot; // 实际是 _WarmSlot，只在 cutover_engine.dart 内解开
  final int _op;
}

/// 提交结果：区分"没就绪"和"已被更新的操作取代"。
enum MovaWarmCommit { committed, notReady, superseded }

/// 能按凭据提交的切换实现（包内可选能力，公开 MovaCutover 不加成员）。
abstract interface class MovaWarmOwner {
  /// 同 prepare；触发器拒绝、已关闭或已销毁时返回 null。同源在途预热返回同一凭据。
  Future<MovaWarmTicket?> prepareOwned(MovaSource source,
      {Duration at, MovaWarmCue cue, MovaWarmPlan plan});

  /// 只提交 [ticket] 对应的槽；槽已被换走按 notReady，操作代际变了或已销毁按 superseded。
  Future<MovaWarmCommit> commitOwned(MovaWarmTicket ticket, {bool waitForReady});
}
```

实现直接复用 F1 的 `_startWarm`（已返回 `_WarmSlot?`）与 `_commitSlot(slot, op)`；`commitOwned` 在 `_commitSlot` 返回 false 后看 `_disposed || ticket._op != _op` 决定 `superseded`。若 F4 已经引入了包内能力接口（"借包内可选能力接口传结果"），A27 在**同一个接口**上加这两个方法，不另起文件（第 9 节第 1 条需要主会话现在就转告 F4 的落地方）。

会话侧：`cutover is MovaWarmOwner` 时走凭据路径；否则（`FakeCutoverCtl`、宿主自写 `MovaCutover`）退回公开 `prepare + commit(waitForReady: true)`，并保留 `_landing` 标志挡住落地窗口内的正片预热（现有 `_landingAd` 语义）。

否决：
- **只用公开 prepare+commit + `_landing` 守卫**：挡得住会话自己的预热，挡不住宿主直接 `open`/`prepare`，"过期不回落"做不到。
- **继续用 `cutoverTo`、只修参数**：`cutoverTo(source, {at, rate})` 带不进 `pauseWhenReady` 与 `adReadyTimeout`，加参数又破坏所有 `implements MovaCutover`。

### D12 — `MovaLoadOutcome` 加 `failed`

总计划 2.3 写的是 `{accepted, rejected, superseded, disposed}`。正片 `open` 抛出、解析器失败（`contentError`）既不是"被拒"也不是"被取代"，A26 也明确"被拒或被取代不是失败"。加 `failed`，类型是新的，无兼容负担（第 10 节第 4 条）。

判定口径（"接受 ≠ 首帧"，2.6 #1）：`load` 的 Future 在本次加载的首段内容（首条前贴片或正片）落到屏上时完成；
- 本纪元内有一次 `open` 返回 true 或一次提交成功 → `accepted`；
- 首段内容一路被拒、最终回 idle → `rejected`；首段内容抛出/解析失败 → `failed`；
- 等待期间纪元被更晚的 `load/jumpTo` 推进 → `superseded`；会话已销毁 → `disposed`。
前贴片被拒后正片被接受仍算 `accepted`；前贴片接受后正片再失败，`load` 已经以 `accepted` 完成，失败走 `contentError`。

### D13 — `MovaAds.load` 返回 `Future<bool>` 而不多出微任务（A25）

会话内部核心写成泛型：`Future<T> _loadCore<T>(…, T Function(MovaLoadOutcome) map)`，每个返回点 `return map(outcome)`。`MovaSession.load` 传恒等，包内 `movaAdsLoad(session, …)` 传 `(o) => o == MovaLoadOutcome.accepted`。这样 `ads.load` 的完成时机与 A22 后完全一致，不靠 `.then`。

### D14 — 播放列表走会话（A25）

- `MovaPlaylist(api, {MovaAds? ads})`。`ads == null`：旧直连路径**逐字不变**（含"不看 `enabled`"）。
- `ads != null`：构造时 `ads.session.setItems(playlist.items, initialIndex: …)`；`jumpTo/next/previous` 转发给会话；不订阅 `MovaDone`；`autoPlayNext` 由会话的 `contentEnded` 驱动（正片 + 全部后贴片之后，2.6 #8）。`enabled == false` 时 `jumpTo/next/previous/自动连播` 都是 no-op（总计划只点了 next/previous/自动连播，`jumpTo` 同属这条路径，一并处理，第 10 节第 7 条）。
- 下标与 `indexChanges` 只在 `accepted` 且未被取代时前进（2.6 #2 在会话路径复刻）。
- 会话自身的 `autoAdvance` 参数只给直接构造会话的宿主用；`movaSessionForAds` 建出的会话 `autoAdvance` 为假，不会和 `MovaPlaylist` 双推进。

### D15 — 失败仲裁（A26）的分工

照总计划 3.3「A26」：广告节点仍走 `MovaAdFailPolicy`；引擎 recovery 开着时，会话对广告节点的非终结错误不动作，只认 `MovaPlayFailure(action: giveUp)`、终结错误或 `loadTimeout`；正片节点 recovery 开时等引擎，`giveUp` 或 recovery 关时的终结错误 → `contentError` + `MovaNodeFail(failItem)` + 回 idle。同一 `(epoch, node, attempt)` 只结算一次。被拒、被取代不是失败。`fatal` 判据一律用 A13 定下的 `MovaErrorEvent.fatal`。**这改变了 `contentError` 的契约**（A05 起是"解析失败 + 正片 open 抛出"，A26 起加上"正片终结错误"），dartdoc 与 CHANGELOG 同提交改。

### D16 — 换指窗口与补发（A28）

- 认领后、`old.pause()` 之前置 `_handoff = (playing: old.state.playing)`；`_attach` 的 state 订阅在 `_handoff != null` 时把转发状态的 `playing` 覆盖成快照值，`MovaPause` 事件（来自 `old`）在窗口内丢弃。换指（`_attach(shadow)` 之前）清掉；`bail` 时清掉并补发一次 `old` 的真实状态。

/// 可暂停的一次性倒计时：到期由 Timer 驱动，剩余时长按注入时钟计算（包内）。
class MovaAdClock {
  /// [now] 默认 DateTime.now；测试注入跟随 fakeAsync 的时钟。
  MovaAdClock({DateTime Function()? now}) : _now = now ?? DateTime.now;

  final DateTime Function() _now;
  Timer? _timer;
  Duration? _left;      // 上次起表/恢复时的剩余
  DateTime? _since;     // 上次起表/恢复的时刻；暂停时为 null
  void Function()? _onExpire;

  /// 起表 [length]，到期调用 [onExpire]；已在走则先取消。
  void start(Duration length, void Function() onExpire) {
    cancel();
    _onExpire = onExpire;
    _left = length;
    _arm();
  }

  /// 暂停；未在走时为空操作。
  void pause() {
    final since = _since;
    if (since == null || _left == null) return;
    _timer?.cancel();
    _timer = null;
    final left = _left! - _now().difference(since);
    _left = left > Duration.zero ? left : Duration.zero;
    _since = null;
  }

  /// 恢复；未暂停或已取消时为空操作。
  void resume() {
    if (_since != null || _left == null) return;
    _arm();
  }

  /// 取消，之后 [remaining] 为 null。
  void cancel() { _timer?.cancel(); _timer = null; _left = null; _since = null; _onExpire = null; }

  /// 剩余时长；未起表或已取消为 null。
  Duration? get remaining { /* running ? max(0, _left - (now - since)) : _left */ }

  /// 是否正在走。
