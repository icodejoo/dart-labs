# 清晰度无缝切换（bilibili 式）——复杂度预研，不动手实现

**结论先行：可以在不换播放内核的前提下借鉴 ExoPlayer/hls.js 的思路做到，复杂度中等
（量级接近阶段 B/C），核心风险是真机上"要预缓冲多久才够"需要实测调参，不是纯代码
问题。**

## 上次的结论 vs 本次的诉求

上一轮查证（见
[2026-08-04-quality-native-tracks-spike.md](../plans/2026-08-04-quality-native-tracks-spike.md)
附录、[ROADMAP.md](../ROADMAP.md)"技术风险"）确认：mpv/media_kit（以及同门的
ijkplayer）用的 FFmpeg HLS demuxer 是懒加载模型，`setVideoTrack` 本身不会做
ExoPlayer/hls.js 那种"并行预取候选码率分段、在分段边界无感切换"。

用户澄清诉求：**不是要换掉 mpv 换 ExoPlayer/AVPlayer，是要借鉴它们"预取好了再切"的
思路，在现有 media_kit 架构上实现类似效果。**

## 可借鉴的思路：影子引擎预缓冲 + 热切换（不是分段级，是引擎级）

ExoPlayer/hls.js 的无缝切换本质是"新数据已经就位，切换只是把播放头指向新数据"。
mpv 的 Player 不暴露分段粒度的控制，但**mova 项目里已经有一个验证过的同构模式
可以复用**：`lib/src/ui/scope/`（feed 的引擎池）+
`example/lib/spike_dual_engine.dart`——feed 场景里，观众正要划到的下一页视频，
提前在**一个独立的 `MovaEngine`/`Player`**上打开、跑到首帧并停住，用户划过去时直接
展示这个"热"引擎，没有等待感。这个"第二引擎预热+按需展示"的内存代价已经在真机上用
`dumpsys meminfo` 分三阶段测过，SPEC.md 记录为"可接受"（`doc/SPEC.md` 279-284 行）。

**把同一思路搬到清晰度切换**：用户点选清晰度 Q 时，不是原地 `setVideoTrack`，而是：

1. 后台开一个"影子" kernel/Player，打开同一 master playlist，`setVideoTrack(Q)`，
   `seek` 到当前播放位置附近，`autoPlay: false`（或播放但静音，不接显示）。
2. 监听影子引擎的 `buffering`/`position` 流，等它稳定跑到目标位置且不再缓冲
   （类似"预热完成"信号——这是全新逻辑，项目里没有现成的可以直接抄，需要自己定义
   "何时算准备好"的判定，可能要留一点提前量比如 1-2 秒的 lookahead）。
3. 就位后：暂停主引擎，把 `MovaApi.renderHandle` 指向的 `VideoController`
   切换成影子引擎的，恢复播放，销毁旧的主引擎。

## 具体要动的地方（复杂度落点）

- **`MovaKernel.renderHandle`/`MovaApi.renderHandle` 目前是一次性 `late final` 属性**
  （`mpv_kernel.dart:153`、构造期绑死），不是可变/可观察的。要支持热切换，
  `renderHandle` 得能在引擎生命周期中间变更身份，并触发 UI 重建。
  好消息：`lib/src/ui/player.dart` 的 `_RenderSurface` 已经是"每次 build 都重新读
  `api.renderHandle`"（`MovaSelect` 包裹），**不需要重写渲染层**——只需要让
  `renderHandle` 变更时能触发一次现有的重建路径（比如把它纳入触发 `MovaSelect`
  重建的信号里），UI 侧改动比预想的小。
- **`MovaEngine` 需要能同时持有两个 kernel 一小段时间**（当前 kernel + 影子
  kernel），并在切换瞬间把所有转发的流（position/duration/buffer/size/tracks…）
  从"当前生效 kernel"重新指向新 kernel——这是本次改动里最大的一块，属于
  `core/engine.dart` 内部编排逻辑，不涉及公开 API 断裂（`MovaApi` 表面不变，只是
  `switchQuality()` 内部实现换了）。
- **"预热完成"判定**是全新逻辑，类似 `MovaBufferAbr` 但目的相反（判断"已经够顺"
  而非"该降档"），需要新写、新测，且**具体阈值必须真机试**（缓冲多久算够，纯靠
  经验值起步，肯定要调）。
- **资源代价**：切换瞬间有两个解码 session 并存，但只在切换的那一两秒内，比 feed
  引擎池"常驻 N 个热引擎"的稳态代价更低——feed 那次真机测过"可接受"，这次量级更小，
  预计不会是拦路虎，但仍建议真机复测确认。

## 值不值得做

- **好处**：补齐 mova 与主流 App（bilibili/抖音）观感上最后一处明显差距，且是
  真正可以做到的（不是伪需求）。
- **代价**：中等工程量，量级接近阶段 B（拖动预览，15 Task）或阶段 C（直播时移，
  9 Task）——不是小改动，但也不是要重写内核那种大工程。
- **主要风险不是"能不能做"，是"体验调参"**：预热阈值、切换瞬间是否会有一帧跳变/
  音频轻微咔哒声，都要真机反复试才能收敛，可能要来回迭代几轮。

**建议**：如果决定做，下一步是照阶段 B/C 的方式拆一份逐 Task 落地计划（先定
`MovaEngine` 双 kernel 编排的接口形状，再补"预热完成"判定，再接 UI 热切换，最后真机
调参）。这次先停在"复杂度预研"，等用户确认要不要投入再拆计划。

## 2026-09-16 追加：广告场景同构，且应抽成独立可复用模块

聊起广告播完回正片"黑屏+loading"，追问下来发现根因和本节完全同构，一并记录。

### 广告切换 = 同一个问题

`MovaAdCtrl._playContent()`（`lib/src/core/ad/ad_controller.dart:283`）现在只绑一个
`_api`（单引擎），广告结束调 `_api.open(content)`——同一个 `VideoController` 底下
拆了重建一遍解码管线，中间那段就是黑屏/loading。跟清晰度切换是**一模一样的病因**：
"渲染面"绑死在"当下正在播的那个引擎"上，换引擎必然经过一次可见的重建。

**libmpv 自身的缓存救不了这个**：`--demuxer-max-bytes` 之类是挂在"当前打开的
demuxer 实例"上的内存环形缓冲，`open()` 换媒体会连缓存一起释放，不存在"预留一份
给之后切回来用"的机制。真要绕开网络延迟，退一步的方案是自己在应用层缓存字节
（点播 mp4 后台续着下到本地临时文件，`open()` 时指向本地路径；HLS 则要自建本地
缓存代理拦截 manifest/分片）——能去掉网络往返那一截，但解封装/解码器重建的小间隙
还在，不是逐帧无缝，比双引擎方案廉价但不彻底。

**双引擎能做到逐帧无缝的关键**：`_RenderSurface`（`lib/src/ui/player.dart:171-174`）
已经是"每次 build 都读 `api.renderHandle`"喂给 media_kit 的 `Video(controller:)`——
`VideoController` 换了，Flutter 只是换一下合成层用的纹理 id，只要两个
`VideoController` 都已经渲染过帧，切换就是同一帧到下一帧的事，观感上无感知。
这正是本文档前面几节给清晰度切换设计的机制，原样适用于广告。

### 广告场景比 feed 场景更省成本：结束时机可预测

feed 引擎池必须常驻 N 个热引擎，因为"用户什么时候划下一页"不可预测。广告不同——
**广告时长基本已知**，不需要全程双活：

- 只在广告快结束前（例如剩 1-2 秒，由 `MovaAdCtrl.adPosition` 与广告时长算出）才
  去预热正片引擎（`open()` + `seek()` 到续播点），跑到目标帧就 `pause()`——不持续
  解码。多数广告时长里场上只有广告引擎一个在跑，双活窗口压缩到最后一两秒。
- 换完立刻 `dispose()` 旧的广告引擎，不像 feed 池那样保留复用（广告位一次性，没有
  "划回去"的需求）。
- 预热阶段先不接音频轨，真正 swap 时才连上，避免多占一路音频解码资源。
- 广告时长低于某个阈值（比如 5 秒）直接不启用预热，吃那一下黑屏——短广告里"提前
  预热"的窗口本来就没多少，双份开销不值当。

这套"临切换前才短暂重叠"策略不改变双引擎并发那一刻的内存/GPU 峰值（确实是两份），
但把"两份同时存在"的**时长**从"全程"压成"最后一两秒"，大幅降低内存占用的时间积分，
也大幅降低真撞上硬解并发 session 上限（很多中低端 Android SoC 只支持 1-2 个）的
概率。

### 应抽成独立、可开关、可跨模块复用的模块

清晰度切换、广告回切、（未来可能有的）播放列表下一集预加载，需要的都是同一件事：
**一个稳定的渲染面 + 可插拔切换到底层哪个引擎 + 可配置的预热时机策略**。不应该在
`MovaAdCtrl`、`switchQuality()` 里各写一份，应该抽成核心层一个独立单元（暂拟名
`MovaSeamlessSwap` 或类似，落在 `core/` 下，纯 Dart、可单测），职责收敛为：

- 持有"当前生效引擎"与"预热中的影子引擎"，对外暴露**唯一**稳定的
  `renderHandle`/`progress`/`states`（代理转发，UI 侧只认这一份，不关心背后换过谁）。
- 预热时机策略可插拔：广告用"剩余时长倒推"，清晰度切换用"用户选中即触发"，都是
  同一套"预热→就绪判据→原子切换→释放旧引擎"骨架的不同触发/判据实现。
- **默认关闭、可配置开启**（比如 `MovaOpts` 里一个 `seamlessSwap: false` 默认值），
  不想承担双引擎内存/session 代价的宿主可以关掉，退化回现在"直接 open() 重建"的
  行为——即这次讨论的一切都是可选增量，不动现有默认路径。
- `MovaAdCtrl` 与（未来的）`switchQuality()` 都改为在需要热切换时调用这个模块，
  而不是各自内联一套双引擎编排。

### feed 引擎池要不要也改成"一份渲染面对应多个引擎"？——不适用，结论是不改

feed 的"上滑下一页"在拖拽过程中需要**两页同时可见、各自独立跟手动画**（半程手势
时新旧两屏都露出来、随手指位置连续过渡），这要求两个画面**同时存在于渲染树上**；
而清晰度切换/广告回切是"某一瞬间整体切一刀"的离散替换，同一时刻只需要一个画面
可见。"单一渲染面切换指向哪个引擎"这个模型只解决**离散切换**，解决不了"两屏同时
渲染、连续插值"这种**需求本身就要求双画面并存**的场景——不是引擎管理的问题，是
渲染层结构性的差异。

所以结论是：feed 引擎池（`core/feed/engine_pool.dart`）**保持现状**，不套用本节的
单渲染面模型；但底层"引擎生命周期管理"（预热/暂停/销毁）这一层可以与
`MovaSeamlessSwap` 共享同一套原语（比如都复用同一个"影子引擎预热+就绪判据"的
基础设施），只是 feed 在其上派生出多个独立渲染面，`MovaSeamlessSwap` 场景只
维护一个。
