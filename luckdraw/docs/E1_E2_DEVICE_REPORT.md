# E1/E2 真机实验：帧节奏与纹理成本

设备：vivo V2417（Android 16，SDK 36），屏幕 1080×2400，DPR 2.75，**当前显示模式 60Hz**（`renderFrameRate 60`，屏幕另支持更高刷新率，但本次未启用）。
模式：`flutter drive --profile`，Impeller 后端（OpenGLES）。原始数据：`docs/device/e1_e2/`。

## E1：九宫格高亮的帧节奏

方法：`LuckyGrid`（首页九宫格配置，300×300 逻辑像素）play 后巡航 6 秒；记录每帧 vsync 时间戳、`activeIndex`、`FrameTiming`。

| 指标 | 结果 |
| --- | --- |
| 巡航帧间隔 | 中位 16.666ms，p95 16.673ms，max 16.757ms，**丢帧（>1.5×）0 / 359** |
| build / raster | build 均值 0.97ms（p95 1.92）；raster 均值 6.12ms（p95 8.34） |
| 单帧总耗时 | p95 11.49ms；max 74.7ms（首帧） |
| **高亮每格停留** | 168 次换格，**全部恰好 2 帧（33.33ms，min/median/max = 33.32/33.33/33.42）** |

结论：
1. 60Hz 下帧率非常稳定，**没有丢帧，也没有 2/3 帧交替**。此前在无头模拟时钟里看到的"2/3 帧交替"不适用于真机巡航；**修正**我之前"节奏取整导致抖动"的说法。
2. 巡航时高亮以固定 **30 次/秒** 切换（每格 33ms）。这远高于 WCAG 2.3.1 的 3 次/秒闪烁阈值，是视觉"抖/闪"感和光敏风险的主因（频率与对比度，而不是帧不均匀）。
3. 此前"120Hz 会更平滑"的推测未验证：本机系统当前是 60Hz，没有切换到 120Hz 测。

## E2：单张纹理的真实成本

方法：在真机上创建 K 张 825×825（= 300 逻辑像素 × DPR 2.75 向上取整）RGBA 纹理（`toImageSync`，随机内容避免压缩），每帧画一遍（持续重绘），每阶段采样 `dumpsys meminfo` 并记录光栅耗时。

| 纹理数 K | 名义显存（w×h×4） | raster 均值 | raster p95 | 总耗时 p95 |
| --- | --- | --- | --- | --- |
| 0（基线） | 0 | 4.31ms | 5.67ms | 9.81ms |
| 1 | 2.6 MiB | 5.20ms | 7.05ms | 10.80ms |
| 5 | 13.0 MiB | 5.98ms | 7.31ms | 10.85ms |
| 10 | 26.0 MiB | 5.84ms | 7.33ms | 10.91ms |
| 20 | 51.9 MiB | 6.01ms | 7.29ms | 11.09ms |
| **40** | **103.9 MiB** | **16.58ms** | **18.38ms** | **28.99ms** |
| 释放后 | 0 | 2.64ms | 3.28ms | 7.75ms |

结论：
1. **存在明显断崖**：名义纹理总量到 52 MiB 以内，光栅耗时平稳；到 104 MiB，光栅耗时翻 2.8 倍，帧耗时 p95 29ms（掉帧）。断崖位于 52～104 MiB 之间（本机），推测是 GPU 资源缓存超出预算后每帧换入换出。
2. **`dumpsys meminfo` 测不到 GPU 纹理**：40 张名义 104 MiB，App 的 Graphics 只增长约 4.8 MB，TOTAL PSS 增长约 22 MB。不能用它估算显存，预算应基于名义字节数公式 `ceil(W×DPR)×ceil(H×DPR)×4`。
3. 释放后光栅耗时回落，说明资源可回收。
4. 基线（几乎空画面 + 持续重绘）的光栅耗时就有 4.3ms，所以 E1 里九宫格的 6.1ms 光栅耗时中，**九宫格自身约 1.8ms**。把地图烘成一张纹理最多省这一部分，收益有限（约 1～2ms/帧）。

## E3：plane 纹理化的可行性替身实测

目的：在不实现 plane API 的前提下，估算"地图烘成一张纹理 + 只画高亮框"的收益上限。方法：同机同模式（profile、60Hz），三个场景都用同一个 `Ticker` 持续触发重绘，各测 5 秒：
- C 空画面基线；
- A 现有 `LuckyGrid` 转动（首页配置，300×300）；
- B 替身：静止时用 `RepaintBoundary.toImage(pixelRatio: dpr)` 抓一张整图，每 2 帧画一次"整图 + 红色高亮框"。

| 场景 | 被光栅的帧数 / 5s | raster 均值 | raster p95 | build 均值 | 总耗时 p95 |
| --- | --- | --- | --- | --- | --- |
| C 空画面基线 | 149 | 3.97ms | 7.92ms | 0.74ms | 13.70ms |
| A 现有九宫格转动 | 127 | 5.29ms | 8.48ms | 0.95ms | 13.49ms |
| B 纹理 + 高亮框 | 301 | 2.92ms | 3.43ms | 1.30ms | 7.40ms |

读数时要注意的混杂因素：
1. **A、C 被光栅的帧数只有约一半**（约 30 帧/秒），而 B 是 60 帧/秒。原因是 A 的画面只有高亮换格（30 次/秒）时才有像素变化，引擎会跳过无变化的帧；B 每帧都重画矩形，所以每帧都被光栅。因此"每帧耗时"不能直接对比，应看**每秒总光栅耗时**：A ≈ 127/5×5.29 ≈ 134ms/s，B ≈ 301/5×2.92 ≈ 176ms/s。
2. 空画面基线（3.97ms）比 B（2.92ms）还高，说明同机单次测量的噪声约 ±1ms，差距在 1～2ms 量级的结论不应过度解读。

结论：
- 在**每帧都有变化**的前提下，纹理 + 高亮框的单帧光栅耗时约为现有九宫格的一半（2.9ms 对 5.3ms），p95 总耗时从 13.5ms 降到 7.4ms，**能多出约 6ms 的帧预算余量**；
- 但本机现有九宫格已在预算内（p95 总耗时 13.5ms < 16.7ms，无丢帧），且高亮只有 30 次/秒变化时引擎本就会跳过一半的帧；
- 所以**在这台机型上 plane 纹理化不是刚需，收益是余量**。决定：**暂不实现 core 的 plane API**；保留设计（见 docs/audit/planes.md）作为低端机或每帧都有动效的场景的后续选项，等有明确需求或低端机数据再做。

## 对后续决策的含义

- 纹理化预算：以**名义字节数**计，默认应远低于断崖（本机 ≥ 52 MiB 时仍安全，< 104 MiB 才出问题）。建议默认上限取 **32 MiB** 量级；设备相关，应允许用户调大或关闭，而不是写死。
- 九宫格分层的收益见 E3：本机上是余量而非刚需，已决定暂不实现 plane API。
- 高亮切换频率（30 次/秒）作为独立问题处理：已加 `GridOptions.maxStepsPerSecond` 与 `reduceMotion`（默认跟随系统，3 次/秒封顶）；纹理预算已加 `LuckyPerformanceOptions.maxRasterBytes`（默认 32 MiB，共享）。

## 复现

临时测试已删除（`zz_e1_test` / `zz_e2_test` + `test_driver/zz_driver.dart` + 宿主采样脚本）。核心做法：`flutter drive --profile`，E1 用 `SchedulerBinding.addPersistentFrameCallback` 与 `addTimingsCallback`；E2 用 `PictureRecorder` + `toImageSync` 生成纹理，`Ticker` 驱动持续重绘，宿主脚本在 `E2STAGE` 日志行出现时执行 `adb shell dumpsys meminfo`。
