## 规格不清与保守取舍

- 对照 axp 201d192、4ad9182：后者把判断从 disposed 转成共享会话 owners。当前实例卸载而仍有其他持有者时，共享刷新失败清理会话并只通知一次；最后持有者卸载后，旧窗口失败无操作。已有 refreshTimeout、快照保护、重放上限、ready 前后和重放前凭证重查、取消等待保持。
- 与 axp 的差异按 dioman 文档处理：auth 使用 Expando 并在 owners=0 时显式解除关联；axp WeakMap 在该 dispose 中只减 owners。loading 使用可按 == 合并 tear-off 的普通 Map，归零且无窗口即删；不照搬 WeakMap 的函数身份语义。计时器使用安排窗口的客户端 DiomanClock。
- 登录复位按受保护请求观察到当前有 token 执行。TokenManager 接口没有写入事件订阅，无法识别两次请求之间“写入 token 又立即清空”而从未被 auth 观察的过程；未扩展公开接口或恢复宿主机制。
- 同一 TokenManager 安装不同刷新/通知配置时，加入已存在的窗口，由首个发起者的刷新回调、超时、时钟和失败通知处理本轮；这是现有单飞规则在共享资源上的延伸。
- 全部持有者卸载后重新安装，建立新会话；旧窗口即使迟到失败也不能清理新会话，已添加用例固定此边界。用户 onRefresh 自行写 token 的副作用仍归用户所有。

### 需终审确认

1. 插件规格 §4 写“dispose 后迟到失败空操作，不影响其他持有者”，单独阅读容易理解为一律忽略；本任务明确要求仍有持有者时按共享规则处理一次，且与 axp 4ad9182 一致。本实现以本任务细化口径为准；未修改设计文档。
2. TokenManager 无写入事件时，“写入新 token 后复位”采用下一次受保护请求观察复位；如需观测无请求期间的登录/登出循环，需要另定通知契约。
